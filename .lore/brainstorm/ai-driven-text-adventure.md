# Brainstorm: AI-driven persistent text adventure

## Context

Seed idea (`.lore/ideas/2026-04-16.md`): a classic MUD with a persistent world fully generated by AI. Opened up the scope, then narrowed it. Arrived at a Zork-like single-player conversational adventure where AI extends — not replaces — classic text-adventure mechanics.

## Ideas Explored

### Scope narrowing: MUD → Zork+

Started with MUD (multiplayer, persistent, AI-generated). Pulled back to single-player conversational adventure. Rationale: multiplayer introduces hard problems (shared-room coherence, shared NPC state, exploit economies) that distract from the core design question. Single-player lets AI do what it's actually good at — prose, characters, narrative — without fighting consistency at scale.

### The central design challenge: stochastic vs deterministic boundary

Every feature must answer: *which side is it on, and why?* This is the game's north star, not a detail.

Rough working split:
- **Deterministic (engine):** world map (rooms, exits, item locations), inventory, NPC existence and location, narrative state flags, parser → action resolution.
- **Stochastic (AI):** room descriptions on first entry, NPC dialogue, narrative beats, new territory generation.

Not settled. The boundary will shift during iteration.

### Persistence as mechanism, not feature

Base area is hand-authored. AI generates on exploration. Once generated, content is written to a persistent store (files or DB) and becomes canon — the AI re-reads it like any other room and never regenerates it.

Persistence is what makes the multi-agent architecture cheap: agents don't need to share context because the store *is* the shared context. Storage schema = game's memory architecture.

### Multi-agent architecture with narrow context

Single omniscient agent is expensive and inefficient. Instead: several specialized agents, each with a narrow role and narrow context window. Each loads the slice of the store that matters, acts, writes back.

Sketch (not committed — exact count and roles will iterate):
- **World Author** — rare calls. Generates new rooms from adjacent rooms + style guide + player-prompt seed.
- **Narrator/Director** — periodic. Reads event log, decides when plot beats should fire. Ideally fires events (deterministic) rather than suggestions (stochastic cascade).
- **NPC Voice** — per conversation. Loads that NPC's `identity.md` + `journal.md` + last N turns. Writes journal deltas back.
- **Action Resolver** — every turn. Translates player's free-form input to a canonical action the engine understands.

### Input: natural language, not `take lamp`

Old-Zork command syntax was a technical limitation, not a design choice. LLMs remove that constraint. Player writes freely; engine canonicalizes.

### Player-authored setup

Base plot can be pre-set, or the player fills a structured prompt at game start (setting, tone, protagonist, central tension, forbidden things). That becomes the style guide every agent sees. The base area is generated from it before play starts.

### Method: implementation as exploration

Agent count, agent roles, noun-handling policy, narrator behavior, persistence granularity — these aren't decisions to settle in a doc. They're hypotheses to test in running code. Plan: agree on base vision, then minimal atomic steps, test each, iterate.

## Open Questions

1. **Noun coherence ("the AI lied about a bookshelf").** Player types `climb bookshelf`. The prose mentioned it; the engine's structured room data doesn't. Reject? Promote to scenery? AI re-checks before accepting? This is load-bearing — it determines whether the game is a game or a chatbot in a trench coat. Expected to iterate.

2. **NPC knowledge boundaries.** When a player asks an NPC about a room they've never visited, does NPC Voice need access to World Author's output? Or do NPCs only know what's in their journal, and say "I don't know"? Cleaner vs. sometimes-dumb.

3. **Narrator risk.** A bad narrator railroads. A timid one lets the game drift. Events-only with tight triggers feels safer than stochastic suggestions — but needs validation.

4. **Persistence granularity.** File-per-room is obvious. What about *changes* to rooms (player burns down the inn)? Overwrite? Versioned? Deltas-log? Hard vs soft persistence layers.

5. **Player-prompt lifespan.** One-shot stories per prompt, or persistent sandbox across sessions?

- Identify the minimal atomic first step — probably: hand-authored base area + deterministic engine + simplest possible Action Resolver agent, no generation yet. Prove the loop before adding AI generation.

### Base vision (proposed for vision doc)

1. **Shape:** single-player, conversational text adventure (Zork+, not MUD).
2. **Input:** natural language; engine canonicalizes to actions.
3. **Core loop:** engine holds deterministic world state; AI generates prose, dialogue, and new territory on demand.
4. **Persistence:** files/DB as source of truth; AI-generated content is written once, re-read thereafter.
5. **Architecture stance:** multiple specialized agents with narrow context. Specific count and roles TBD through iteration.
6. **Design north star:** the stochastic/deterministic boundary is where this game lives or dies. Every feature must answer which side it's on.
7. **Method:** minimal atomic steps, test each, iterate. Implementation is part of the exploration.
